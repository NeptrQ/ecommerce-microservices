E-Commerce Microservices on Kubernetes

How a request travels from the client to MongoDB Atlas, and how every pod writes its request log to its own /shared-logs volume for a BusyBox sidecar to read. Taken from the manifests in kubernetes/ and the service code.

How the logs flow

  • utils/logger.js runs as Express middleware in every service. When a response finishes it builds one line: time, service, method, path, status, duration.
  • It prints that line to stdout and appends it to $LOG_DIR/<service>.log, where LOG_DIR=/shared-logs.
  • The log-reader sidecar mounts the same volume read-only, waits for the file to appear, then runs tail -F on it.
  • The gateway runs 2 replicas, so there are 2 separate gateway.log files, one in each gateway pod.

Read the logs

kubectl logs -n ecommerce deploy/auth-service -c log-reader -f

kubectl exec -n ecommerce deploy/auth-service \
  -c auth-service -- cat /shared-logs/auth-service.log

Request path

  • ecommerce.com resolves through your /etc/hosts entry, not a DNS server.
  • The Ingress has one rule, / → gateway-service:5011. The API Gateway does the per-path routing.
  • The gateway checks the JWT (and the admin role for product writes and order updates) before forwarding. Order and Product check the JWT again.
